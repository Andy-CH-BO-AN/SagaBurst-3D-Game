# GLOSSARY.md 格式

## 結構

```md
# {上下文名稱}

{用一到兩句話描述這個上下文是什麼，以及它存在的原因。}

## 用語

**訂單（Order）**：
{用一到兩句話描述這個術語}
_避免使用_：購買（Purchase）、交易（transaction）

**發票（Invoice）**：
交付後寄給客戶的付款要求。
_避免使用_：帳單（Bill）、付款請求（payment request）

**客戶（Customer）**：
下訂單的個人或組織。
_避免使用_：委託人（Client）、買方（buyer）、帳戶（account）
```

## 規則

- **明確選定用語。** 同一個概念有多種說法時，選擇最適合的一個，並將其他說法列在 `_避免使用_` 下。
- **定義保持精簡。** 最多一到兩句。定義它是什麼，而不是它做什麼。
- **只收錄這個專案上下文特有的術語。** 一般程式設計概念（逾時、錯誤類型、工具模式）不應列入，即使專案大量使用它們也一樣。新增術語前，先問：這是這個上下文特有的概念，還是一般程式設計概念？只收錄前者。
- **出現自然的群組時，用小標題整理術語。** 如果所有術語都屬於同一個緊密相關的領域，用平鋪清單即可。

## 單一與多個上下文的儲存庫

**單一上下文（大多數儲存庫）：** 儲存庫根目錄放一份 `GLOSSARY.md`。

**多個上下文：** 儲存庫根目錄的 `GLOSSARY-MAP.md` 列出各上下文、所在位置，以及彼此的關係：

```md
# 詞彙表對照

## 上下文

- [訂單處理（Ordering）](./src/ordering/GLOSSARY.md)：接收並追蹤客戶訂單
- [帳務（Billing）](./src/billing/GLOSSARY.md)：產生發票並處理付款
- [履約（Fulfillment）](./src/fulfillment/GLOSSARY.md)：管理倉庫揀貨與出貨

## 關係

- **訂單處理 → 履約**：訂單處理發出 `OrderPlaced` 事件；履約接收事件後開始揀貨
- **履約 → 帳務**：履約發出 `ShipmentDispatched` 事件；帳務接收事件後產生發票
- **訂單處理 ↔ 帳務**：共用 `CustomerId` 與 `Money` 的型別
```

這項技能會推斷應採用哪種結構：

- 如果存在 `GLOSSARY-MAP.md`，就閱讀它來找出各上下文。
- 如果只有根目錄的 `GLOSSARY.md`，就是單一上下文。
- 如果兩者都不存在，就在第一個術語確定時，才於根目錄建立 `GLOSSARY.md`。

有多個上下文時，推斷目前討論的主題屬於哪一個。如果不清楚，就詢問使用者。
