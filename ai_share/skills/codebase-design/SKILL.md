# 程式碼庫設計

設計**深層模組**：將大量行為放在精簡介面背後，將介面設置於清楚的接縫，並透過這個介面進行測試。凡是設計或重組程式碼，都使用這套詞彙與原則。目標是為呼叫端帶來槓桿效益、為維護者帶來局部性，並讓所有人都能輕鬆測試。

## 詞彙表

請嚴格使用以下術語，不要改稱「元件（component）」、「服務（service）」、「API」或「邊界（boundary）」。用語一致正是這套詞彙的目的。

**模組（Module）**：任何具有介面與實作的事物。刻意不限定規模：可以是函式、類別、套件，或橫跨多個層級的功能切片。_避免使用_：單元、元件、服務。

**介面（Interface）**：呼叫端為了正確使用模組而必須知道的一切，不只包括型別簽章，也包括不變條件、順序限制、錯誤情況、必要設定與效能特性。_避免使用_：API、簽章（這些詞太狹窄，只指型別層面的使用方式）。

**實作（Implementation）**：模組內部的程式碼。它與**轉接器**不同：一個事物可以是實作龐大的小型轉接器（例如 Postgres 儲存庫），也可以是實作精簡的大型轉接器（例如記憶體內的測試替代品）。討論接縫時使用「轉接器」，其他情況則使用「實作」。

**深度（Depth）**：介面所帶來的槓桿效益。呼叫端或測試每學會一單位介面，就能運用多少行為。大量行為藏在精簡介面背後的模組稱為**深層（deep）**；介面複雜程度幾乎與實作相當的模組稱為**淺層（shallow）**。

**接縫（Seam）**_（Michael Feathers）_：可以在不修改該處程式碼的情況下，改變該處行為的位置；也就是模組介面所在的*位置*。接縫放在哪裡，是獨立的設計決策，與接縫背後放什麼不同。_避免使用_：邊界（這個詞也用於領域驅動設計 DDD 的限界上下文，容易混淆）。

**轉接器（Adapter）**：在接縫處滿足介面的具體事物。描述的是*角色*（填入哪個位置），而非內容（裡面有什麼）。

**槓桿效益（Leverage）**：深度為呼叫端帶來的效益。每學會一單位介面，就能獲得更多能力。一份實作能讓 N 個呼叫位置與 M 個測試共同受益。

**局部性（Locality）**：深度為維護者帶來的效益。變更、錯誤、知識與驗證集中在一處，而非分散到各個呼叫端。修正一次，所有地方都得到修正。

## 深層與淺層

**深層模組** = 精簡介面 + 大量實作：

```text
┌─────────────────────┐
│      精簡介面       │  ← 方法少、參數簡單
├─────────────────────┤
│                     │
│      深層實作       │  ← 隱藏複雜邏輯
│                     │
└─────────────────────┘
```

**淺層模組** = 龐大介面 + 少量實作（應避免）：

```text
┌─────────────────────────────────┐
│            龐大介面             │  ← 方法多、參數複雜
├─────────────────────────────────┤
│            薄弱實作             │  ← 只是轉交呼叫
└─────────────────────────────────┘
```

設計介面時，問自己：

- 能否減少方法數量？
- 能否簡化參數？
- 能否將更多複雜度隱藏在內部？

## 原則

- **深度是介面的特性，而非實作的特性。** 深層模組內部可以由小型、可模擬、可替換的部分組成；只是這些部分不屬於介面。模組除了介面處的**外部接縫**，也可以有**內部接縫**（僅供實作內部使用，並由模組自身的測試使用）。
- **刪除模組的檢驗法。** 想像把模組刪掉。如果複雜度隨之消失，這個模組只是轉交呼叫。如果複雜度重新出現在 N 個呼叫端，這個模組就有存在的價值。
- **介面就是測試範圍。** 呼叫端與測試穿越同一個接縫。如果你想越過介面測試內部，模組的形狀很可能不合適。
- **不要為假想轉接器新增接縫。** 正式儲存與測試用記憶體儲存是實際替換需求；若只有一個實作，需說清楚接縫提供的測試隔離或職責價值，不能只為未來擴充新增間接呼叫。

## 為可測試性而設計

良好的介面能讓測試自然而然地進行：

1. **接收依賴，不要自行建立依賴。**

   ```typescript
   // 容易測試
   function processOrder(order, paymentGateway) {}

   // 難以測試
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **可分離的規則優先回傳結果，必要副作用由明確擁有者執行。**

   ```typescript
   // 容易測試
   function calculateDiscount(cart): Discount {}

   // 難以測試
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **精簡介面。** 方法越少，所需的測試越少；參數越少，測試準備越簡單。

## 關係

- 一個**模組**恰好有一個**介面**（提供給呼叫端與測試的使用範圍）。
- **深度**是**模組**的特性，以其**介面**為衡量基準。
- **接縫**是**模組介面**所在的位置。
- **轉接器**位於**接縫**處，並滿足**介面**。
- **深度**為呼叫端帶來**槓桿效益**，為維護者帶來**局部性**。

## 不採用的觀點

- **以實作行數與介面行數的比例衡量深度**（Ousterhout）：這會獎勵刻意膨脹實作的做法。我們改以槓桿效益衡量深度。
- **將「介面」等同於 TypeScript 的 `interface` 關鍵字，或類別的公開方法**：這種理解太狹窄；這裡的介面包含呼叫端必須知道的每一項資訊。
- **「邊界」**：這個詞也用於 DDD 的限界上下文，容易混淆。請說**接縫**或**介面**。
