# 改善程式碼庫架構

找出架構上的阻力，提出**深化機會**：透過重構，把淺層模組變成深層模組。目標是改善可測試性，並讓 AI 更容易理解及探索程式碼庫。

這個指令以專案的領域模型為依據，並建立在共用的設計詞彙上：

- 呼叫 [`codebase-design` 技能](../codebase-design/SKILL.md)，取得架構詞彙（**模組**、**介面**、**深度**、**接縫**、**轉接器**、**槓桿效益**、**局部性**）及其原則（刪除模組的檢驗法、「介面就是測試範圍」、「一個轉接器代表假想的接縫，兩個轉接器才代表實際的接縫」）。每項建議都要精確使用這些詞彙，不要改稱「元件」、「服務」、「API」或「邊界」。
- `GLOSSARY.md` 中的領域語言用來為合適的接縫命名；`docs/adr/` 中的架構決策紀錄（ADR）則記載了本指令不應重新爭論的決策。

## 流程

### 1. 探索

**先決定範圍，再掃描：遵循 YAGNI，只處理實際需要的事。** 深化模組的價值，在於讓未來修改它更容易，因此要優先關注最近經常變動的部分。開始查看之前，先決定*要看哪裡*：

- 如果使用者已指定方向（模組、子系統或痛點），就依照該方向，略過下方的推斷步驟。
- 否則，往回查看一段足夠長的提交歷史（`git log --oneline`），找出程式碼庫的變動熱點，也就是反覆出現的檔案與區域，優先關注這些路徑。如果變更很分散，沒有明顯熱點，再擴大範圍。

先閱讀專案的領域詞彙表（`GLOSSARY.md`），以及要處理區域內的 ADR。

接著派出一個子代理探索程式碼庫。不要套用僵化的判斷規則；順著程式碼自然探索，記錄遇到的阻力：

- 理解哪個概念時，必須在許多小模組之間來回跳轉？
- 哪些模組是**淺層**的，介面的複雜度幾乎與實作相同？
- 哪些純函式只是為了方便測試而被抽出，但真正的錯誤藏在呼叫方式裡，缺乏**局部性**？
- 哪些緊密耦合的模組，讓內部細節跨越接縫洩漏？
- 哪些部分沒有測試，或很難透過目前的介面測試？

對任何疑似淺層的模組套用**刪除模組的檢驗法**：刪掉它，會讓複雜度集中，還是只是把複雜度搬到別處？「會集中」才是你要找的訊號。

### 2. 用 HTML 報告呈現候選項目

將報告寫成單一 HTML 檔案，放在作業系統的暫存目錄，避免寫入儲存庫。從 `$TMPDIR` 取得暫存目錄；若沒有設定，使用 `/tmp`（Windows 則用 `%TEMP%`）。檔名為 `<tmpdir>/architecture-review-<timestamp>.html`，確保每次執行都產生新檔案。替使用者開啟它（Linux：`xdg-open <path>`；macOS：`open <path>`；Windows：`start <path>`），並告知絕對路徑。

報告透過 **CDN 載入 Tailwind** 處理版面與樣式，並在圖形、流程或時序能清楚表達結構時，透過 **CDN 載入 Mermaid**。搭配 Mermaid 與手工製作的 CSS／SVG 圖：呼叫圖、依賴關係、時序等圖狀關係用 Mermaid；需要更有編排感的視覺呈現（量體圖、剖面圖、收合動畫）則用自行製作的 div／SVG。每個候選項目都要有**修改前後的視覺比較**。用圖說明。

每個候選項目以卡片呈現，包含：

- **檔案**：涉及哪些檔案或模組。
- **問題**：目前架構為何造成阻力。
- **解法**：用平易的中文描述會改變什麼。
- **效益**：用局部性與槓桿效益說明收益，以及測試會如何改善。
- **修改前／修改後圖**：並排、自行設計的圖，呈現模組如何由淺層變成深層。
- **推薦程度**：用徽章標示「強烈推薦」、「值得探索」或「推測性」。

報告最後加上**首選建議**：你會先處理哪個候選項目，以及原因。

**領域用語採用 `GLOSSARY.md` 的詞彙；架構用語採用 `codebase-design` 的詞彙。** 如果 `GLOSSARY.md` 定義了「訂單」，就稱為「訂單受理模組」，不要稱為「FooBarHandler」，也不要稱為「訂單服務」。

**ADR 衝突**：只有當實際阻力大到值得重新檢視 ADR 時，才提出違反現有 ADR 的候選項目。要在卡片上清楚標示，例如警示框：「與 ADR-0007 衝突，但因為……，值得重新討論。」不要列出所有被 ADR 禁止的理論性重構。

完整 HTML 範本、圖形模式與樣式指引，見 [HTML 報告格式](HTML-REPORT.md)。

此時**不要提出介面設計**。寫好報告後，詢問使用者：「你想深入探索哪一項？」

### 3. 逐步追問

使用者選定候選項目後，呼叫 [`grilling` 技能](../grilling/SKILL.md)，與使用者逐步走過決策樹：限制、依賴關係、深化後的模組形狀、哪些內容藏在接縫後面，以及哪些測試應保留。

決策一旦明確，就立即處理相關更新；呼叫 [`domain-modeling` 技能](../domain-modeling/SKILL.md)，在討論過程中維持領域模型的最新狀態：

- **深化後的模組要以 `GLOSSARY.md` 尚未收錄的概念命名？** 將術語加入 `GLOSSARY.md`。若檔案不存在，等到需要寫入時才建立。
- **討論中釐清了模糊術語？** 當下就更新 `GLOSSARY.md`。
- **使用者以會影響未來判斷的重要理由否決候選項目？** 提議記錄 ADR，例如：「要把這個決定記成 ADR，讓未來的架構審查不再提出同樣建議嗎？」只有當未來探索者確實需要這個理由，才能避免重複提出相同建議時，才提議記錄。略過暫時性理由（「現在不值得做」）及不言自明的理由。
- **想探索深化後模組的不同介面？** 呼叫 [`codebase-design` 技能](../codebase-design/SKILL.md)，使用其中「設計兩次」的平行子代理模式。
